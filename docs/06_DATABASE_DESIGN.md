# 06 — Data and Storage Design

Three stores, three different jobs. None of them is a general-purpose application database, because the pipeline has no application state to keep.

| Store | Technology | Holds | Committed to git? |
| --- | --- | --- | --- |
| Raw dataset | CSV on disk | the training data | **No** — third-party licence |
| Prediction log | SQLite | every score served, plus outcomes | **No** — contains input data |
| Model registry | files + MLflow | the shipped model, its card, run history | **No** — build artifacts |

## 1. Raw dataset — `data/raw/Leads.csv`

Source: the X Education lead-scoring dataset (Kaggle). **9,240 rows × 37 columns.** Target `Converted`, 38.54% positive.

Not in the repo, for two reasons: it is someone else's data to distribute, and a 9k-row CSV in git history is a smell reviewers notice. The README carries download steps; `schema.py` verifies what arrives.

### Contract enforced by `schema.py`

| Column | Type | Constraint | Admissible as a feature |
| --- | --- | --- | --- |
| `Prospect ID` | string | unique, not null | No — join key only |
| `Lead Number` | int | unique | No |
| `Converted` | int | ∈ {0, 1}, not null | **target** |
| `Lead Origin` | category | not null | Yes |
| `Lead Source` | category | nullable | Yes |
| `Do Not Email`, `Do Not Call` | category | ∈ {Yes, No} | Yes |
| `TotalVisits` | float | ≥ 0, nullable | Yes |
| `Total Time Spent on Website` | int | ≥ 0, not null | Yes |
| `Page Views Per Visit` | float | ≥ 0, nullable | Yes |
| `Specialization`, `What is your current occupation`, `What matters most to you in choosing a course`, `City`, `Country` | category | nullable, `"Select"` → null | Yes, with care |
| `How did you hear about X Education` | category | nullable | Low value — 78.5% empty counting `"Select"` |
| `Last Activity`, `Last Notable Activity` | category | nullable | Test both ways |
| 12 ad / opt-in flags | category | ∈ {Yes, No} | Only if not near-constant |
| `Tags`, `Lead Quality` | category | nullable | **No — leakage** |
| `Asymmetrique Activity Index`, `Asymmetrique Profile Index`, `Asymmetrique Activity Score`, `Asymmetrique Profile Score` | mixed | nullable | **No — leakage** |
| `Lead Profile` | category | nullable | **No — 74.2% empty** |

Rules applied in order, before any model sees a row:

1. `"Select"` → null, in every object column.
2. Drop the banned and dropped columns listed above, using the config feature list.
3. Validate types and ranges; any violation aborts the run naming the column.
4. Log row count and target rate; warn if they drift from 9,240 / 38.54% by more than a configured tolerance.

Missing-value rates to expect: `Lead Quality` 51.6%, the four `Asymmetrique` columns 45.7%, `Tags` 36.3%, current occupation 29.1%, `Country` 26.6%, `Specialization` 15.6%.

Derived files in `data/interim/` and `data/processed/` are also git-ignored; nothing in them is a source of truth, so any of them can be deleted and regenerated by `make train`.

## 2. Prediction log — SQLite

**Purpose:** make the pipeline measurable once it is serving, and collect real outcomes that become future training rows.

```sql
-- every lead scored, one row per lead per call
CREATE TABLE IF NOT EXISTS predictions (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    prospect_id     TEXT    NOT NULL,
    scored_at       TEXT    NOT NULL,              -- ISO 8601, UTC
    model_version   TEXT    NOT NULL,              -- e.g. lgbm-2026-11-26
    score           INTEGER NOT NULL CHECK (score BETWEEN 0 AND 100),
    probability     REAL    NOT NULL CHECK (probability BETWEEN 0 AND 1),
    grade           TEXT    NOT NULL CHECK (grade IN ('A','B','C')),
    reasons_json    TEXT    NOT NULL,              -- the 3 reasons as returned
    input_json      TEXT    NOT NULL,              -- the validated request payload
    latency_ms      INTEGER NOT NULL,
    request_id      TEXT                           -- groups a batch call together
);

CREATE INDEX IF NOT EXISTS idx_pred_prospect ON predictions (prospect_id);
CREATE INDEX IF NOT EXISTS idx_pred_scored_at ON predictions (scored_at);
CREATE INDEX IF NOT EXISTS idx_pred_model ON predictions (model_version);

-- outcomes arriving later, from POST /feedback
CREATE TABLE IF NOT EXISTS feedback (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    prospect_id     TEXT    NOT NULL,
    converted       INTEGER NOT NULL CHECK (converted IN (0, 1)),
    reported_at     TEXT    NOT NULL,              -- ISO 8601, UTC
    note            TEXT,
    prediction_id   INTEGER REFERENCES predictions (id)
);

CREATE INDEX IF NOT EXISTS idx_fb_prospect ON feedback (prospect_id);
CREATE UNIQUE INDEX IF NOT EXISTS idx_fb_once ON feedback (prospect_id, prediction_id);
```

Design notes, with reasons:

- **Two tables, not one.** A score is a fact at a point in time; an outcome arrives later and may never arrive. Keeping them apart means feedback never rewrites history, and live accuracy is an explicit join.
- **`input_json` stored whole**, not as 20 columns. The admissible feature list will change between model versions; a JSON blob survives that, and the schema does not need migrating every time the model does.
- **`model_version` on every row.** Accuracy is only meaningful per model. Without this column the log is unusable the moment a second model ships.
- **Timestamps are ISO 8601 UTC strings.** SQLite has no datetime type; text in a fixed format sorts correctly and is unambiguous across machines. See OQ-6 on display timezone.
- **`UNIQUE (prospect_id, prediction_id)`** stops the same outcome being reported twice and double-counting in live accuracy.
- **Latency stored per request** so NFR-1's p95 is measured from real traffic, not a benchmark.
- **Writes never block a score.** If the insert fails, the score is still returned and the failure is logged at `ERROR`. The log is observability, not the product.

Ownership: only `api/store.py` touches these tables. No other module imports sqlite3. That boundary is what makes the capstone's swap to Postgres a one-file change.

### Queries this schema has to answer

```sql
-- live accuracy for one model version
SELECT p.model_version,
       COUNT(*)                                   AS scored_and_known,
       AVG(f.converted)                           AS actual_rate,
       AVG(p.probability)                         AS predicted_rate
FROM predictions p
JOIN feedback f ON f.prospect_id = p.prospect_id
GROUP BY p.model_version;

-- did the top grade actually convert better?
SELECT p.grade, COUNT(*) AS n, AVG(f.converted) AS conversion_rate
FROM predictions p
JOIN feedback f ON f.prospect_id = p.prospect_id
GROUP BY p.grade
ORDER BY p.grade;

-- p95 latency, most recent 10k requests
SELECT model_version, COUNT(*) AS n,
       MAX(latency_ms) AS worst
FROM (SELECT * FROM predictions ORDER BY id DESC LIMIT 10000)
GROUP BY model_version;

-- score drift: daily mean score per model
SELECT substr(scored_at, 1, 10) AS day, model_version,
       COUNT(*) AS n, AVG(score) AS mean_score
FROM predictions
GROUP BY day, model_version
ORDER BY day DESC;
```

## 3. Model registry — files plus MLflow

There is no model database. Two artifacts and a run log are enough, and each is reproducible.

| Artifact | Path | Contents |
| --- | --- | --- |
| Model | `models/model.joblib` | the fitted `Pipeline`: ColumnTransformer + calibrated estimator |
| Model card | `models/model_card.json` | version, training date, data fingerprint, feature list, test metrics, grade cut-offs, stated limits |
| Run history | `./mlruns` (MLflow file store) | every run's params, metrics, plots and model |

`model_card.json` shape — the serving lane reads this, so it is a contract:

```json
{
  "model_version": "lgbm-2026-11-26",
  "trained_at": "2026-11-26T18:40:00Z",
  "trained_by": "make train",
  "data_fingerprint": {"rows": 9240, "columns": 37, "target_rate": 0.3854, "sha256": "<csv hash>"},
  "algorithm": "LightGBM + CalibratedClassifierCV(sigmoid)",
  "feature_set": "shipping",
  "features": ["lead_origin", "lead_source", "total_visits", "total_time_spent_on_website", "page_views_per_visit", "..."],
  "excluded_as_leakage": ["Tags", "Lead Quality", "Asymmetrique Activity Index", "Asymmetrique Profile Index", "Asymmetrique Activity Score", "Asymmetrique Profile Score"],
  "metrics": {"roc_auc": null, "pr_auc": null, "brier": null, "capture_at_20": null},
  "baselines": {"random": {"roc_auc": 0.5, "capture_at_20": 0.20}, "one_rule": {}, "logistic_regression": {}},
  "grade_bands": {"A": {"min_score": null}, "B": {"min_score": null}, "C": {"min_score": 0}},
  "limits": [
    "Ranks leads; it does not decide whether to contact one.",
    "Trained on X Education web leads; untested on any other population.",
    "Excludes all columns a sales rep fills in after contact."
  ]
}
```

`null` values are deliberate: the card is written by a real run, and nothing publishes a metric it has not measured.

**Versioning:** `model_version` is `<algorithm>-<training date>`, stored in the card, returned by `/health` and `/model-info`, and written on every prediction row. Rollback is replacing `models/` with a previous build artifact — no migration, no state to unwind.

## Retention and privacy

The X Education dataset carries no direct identifiers — no names, emails or phone numbers; `Prospect ID` is an opaque key and `City`/`Country` are coarse. So P1 stores no PII, and `input_json` is safe to keep as-is.

That changes the moment this pipeline is pointed at real inquiries (the real-estate carry-over), where a payload may include a phone number. The plan for that case is recorded now so it is not improvised later: hash the identifier before logging, drop free-text fields from `input_json`, and set a retention window. Retention length is OQ-7.
